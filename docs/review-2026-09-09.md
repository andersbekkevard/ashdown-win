# Review, 2026-09-09

Scope: the whole tree as of this date, read in the order README, AGENTS.md, docs, ADRs, then `src/`, `drizzle/`, `scripts/`, `package.json`. `pnpm test` (12 tests), `pnpm typecheck` and `pnpm lint` all pass. Reproductions were done against the local dev server on 127.0.0.1:3100 and the local Docker Postgres only; the rows I created were removed afterwards. Production was not touched.

## 1. How it works

Three append-only tables in Neon Postgres (`src/db/schema.ts`): `players` (name, created_at, unique on `lower(name)`), `matches` (created_at, a1, a2, b1, b2, winner, with CHECK constraints for equal side sizes and distinct players) and `deletions` (match_id, unique). Nothing is ever updated. Every page is `force-dynamic`; on each request `loadLog` (`src/lib/queries.ts:31`) pulls all three tables and `replay` (`src/lib/rating.ts:71`) sorts matches by created_at then id, skips deleted ones, and applies Elo with K 32 for singles and K 16 for doubles using team-mean ratings, producing a current rating and a per-player history. Writes are four Next server actions (`src/app/actions.ts`): `createPlayer` (trim, collapse whitespace, case-insensitive duplicate check, insert), `recordMatch` (zod tuple validation, existence check, insert), `deleteMatch` (existence and already-deleted checks, insert) and `searchPlayers` (escaped ILIKE substring). The client is four pages plus a hand-drawn SVG graph; there is no session, cookie, rate limit, cache or error boundary. Migrations run inside `pnpm build` via `scripts/migrate.mjs`.

## 2. Problems found

### Security and abuse

**Look-alike names defeat the public log.** The only normalisation is `trim` and `\s+` collapse (`actions.ts:23`), and uniqueness is `lower(name)` (`schema.ts:29`). JS `\s` does not match U+200B or U+200D, and nothing applies Unicode NFC. Reproduced locally: `createPlayer("Anders​Bekkevard")` succeeded and the leaderboard then showed two visually identical "Anders Bekkevard" rows; NFC and NFD "José" both created; Cyrillic "А" also passes. The trust model rests on the log being legible, and this breaks it invisibly. NFD is also produced accidentally by some copy-paste paths on macOS, so accented names in an international house can duplicate by accident. Likelihood medium; severity high because it is the one cheat the log cannot show.

**No rate limiting or caps on any write.** Server actions are unauthenticated, their IDs sit in the client bundle, and nothing throttles (`actions.ts` has no middleware; Vercel Hobby has no WAF rate limiting). Reproduced: 15 parallel `createPlayer` calls completed in 0.53 s with all 15 inserted. One script can add ten thousand players (all listed on the home page, `page.tsx:24`) or delete every match, in seconds. Likelihood low in this house but the site and the repo are public; severity high for deletion because it is unrecoverable (next item), medium for player spam.

**Deletion is one tap, unconfirmed, unattributed and irreversible.** `DeleteMatchButton` submits on a single press (`delete-match-button.tsx:10-16`) and sits on every row of the log in the thumb's scroll path (`log/page.tsx:63`). `deletions.match_id` is unique (`schema.ts:67`) and there is no restore event, so the only recovery is the owner with psql. Re-recording appends at the end of the log, so the match changes position and every later rating shifts. Verified by read. Likelihood high (an accidental tap while scrolling the log is near certain within a month); severity medium-high, since "someone deleted my win" and "I deleted it by mistake and can't get it back" are exactly what stops people trusting it.

**Injection and XSS: none found.** Drizzle parametrises everything; the ILIKE escape in `queries.ts:84-87` is correct, reproduced with `%` and `_` returning no rows rather than all rows. React escapes names; `dangerouslySetInnerHTML` only receives build-time markdown from the repo.

**Data exposure: none beyond names.** `.env.production.local` is in the working tree but covered by `.gitignore` line 26. Timestamps reveal when people play, which is the point.

### Reliability

**A database error shows Next's generic "Application error" page and loses the form.** There is no `error.tsx`, `loading.tsx` or `not-found.tsx` under `src/app`. `recordMatch`'s insert (`actions.ts:119`), `deleteMatch`'s two selects (`actions.ts:141-158`) and `createPlayer`'s first `findPlayerByName` (`actions.ts:69`) are outside any try, and both forms await the action with no catch (`record-match-form.tsx:48`, `create-player-form.tsx:16`). The Neon HTTP driver does not retry. Verified by read; I was not permitted to pause the local database to reproduce. Likelihood medium given Neon free-tier scale-to-zero plus Vercel cold starts; severity medium.

**Cold start with no loading state.** Every page is dynamic and hits Neon, which suspends after idle on the free tier. The first scan of the poster on a quiet evening pays function cold start plus database resume with a blank screen. Reasoned. Likelihood high at the poster moment; severity medium because it is the first impression.

**Duplicate matches from slow submits.** Nothing deduplicates `recordMatch`, `submit()` does not check `pending` (`record-match-form.tsx:44`), and after a slow request a user who backs out and retries records two matches. Verified by read. Likelihood medium; severity low-medium, and it compounds the deletion problem.

**The log page is unpaginated with one client form per row.** `log/page.tsx:49` renders every entry with a hydrated `DeleteMatchButton`. Measured locally: 58 KB for 28 matches, about 1.4 KB per row, so 2000 matches is roughly 3 MB of HTML and 2000 forms on a phone. Thirty active players at two matches a week reach that in about a year. Certain if the site succeeds; severity medium.

**The player page loads and replays the whole log twice.** `players/[id]/page.tsx:25` calls `playerPage` and `leaderboard` in parallel, each calling `loadLog` (six queries, two replays). Verified by read. Cheap today, but it doubles Neon round trips on the page people share.

**Preview deploys migrate the production database.** `scripts/migrate.mjs:6-14` runs `drizzle-kit migrate` whenever `DATABASE_URL` is set, and `docs/architecture.md` says the Neon integration sets it for preview as well. A schema change on a branch migrates production before merge. Reasoned. Low likelihood while one person develops; medium severity once residents send PRs.

**Concurrent writes and timezone: fine.** Single-statement inserts, the unique-index race is caught (`actions.ts:85-95`), replay order is deterministic (`rating.ts:51`, tested), and every timestamp is rendered server-side in `America/New_York` (`format.ts:11`, `players/[id]/page.tsx:15`) with DST handled by `Intl`.

### Correctness

**Rating engine: correct.** `expectedScore`, the K choice, the team mean, the shared doubles delta and conservation all match `docs/algorithm.md`, and the twelve tests cover ordering, ties, deletion and conservation. Self-play is blocked three times (`actions.ts:48`, `schema.ts:53`, the UI exclude list). A player with no matches renders a single-point graph and ranks by name among the 1000s.

**Two definitions of "win".** The leaderboard counts `delta > 0` (`queries.ts:66`); the player page uses `winner === side` (`queries.ts:193`). They diverge only when the delta rounds to exactly 0, which I confirmed happens in floating point above a 6400-point gap. Unreachable in practice, but one definition is cheaper than two.

**Creating an opponent from the match form throws the form away.** The "No one called X, Create" link (`player-search.tsx:122`) leaves for `/players/new`, and success pushes to the new player's page (`create-player-form.tsx:18`), so the recorder must return and re-pick both sides. On poster night every opponent is new. Verified by read. Likelihood very high; severity medium because it lands on the one flow that must be effortless.

**Search exclusion happens after the server limit, and an excluded-only hit says "No one called".** The server returns 10 rows (`queries.ts:89`) and the client filters out already-picked ids (`player-search.tsx:92`); if the only hit is the player already on side A, the UI offers to create them, and the create page then says they exist. Reasoned. Low likelihood, mildly confusing.

**Search ranks alphabetically, not by prefix.** Typing "an" lists "Daniel Okafor" and "Hannah Cohen" alongside "Anders". Fine at 12 players, noisier at 200. Low.

### Phone

**Suggestions can render under the fixed dock.** `.sugg` is absolute below the field (`globals.css:173`), the dock is fixed at z-index 80 (`globals.css:317`). On Android the keyboard shrinks the layout viewport; a Side B field scrolled to the bottom edge has its dropdown behind the dock. Reasoned, not device-tested. Medium likelihood.

**Graph tooltip is `white-space: nowrap`** (`globals.css:256`) and holds "Beat Name & Name" for doubles, which can overflow the card on a 360 px screen. Reasoned. Low.

**Fonts load from Google** (`layout.tsx:23-27`). On a slow or filtered network the display font falls back to system fonts; nothing breaks. Low.

## 3. What I would change

### Before the poster goes up

**Make deletion recoverable, and confirm it.** Add a `restores` table (match_id, created_at) and count a match if its latest deletion/restore event is a restore; show "Undo" on deleted rows. Friction: one confirm tap on delete only, none on recording. Code: one migration, a few lines in `replay`, a button. Buys: both accidental and malicious deletion become a public, reversible event, which is the trust model applied to deletion itself. Alternatives: a ten-second undo toast without confirm (less friction, but not durable), or nothing (cheapest; the first griefing incident will be the last).

**Normalise names.** NFKC, strip Unicode categories Cc, Cf and Zs to a single space, reject if empty, then apply the existing lower-case uniqueness. Friction: none. Code: ten lines in `nameSchema` plus a test; existing rows already comply. Buys: removes the only invisible cheat.

**Soft rate limit and hard caps.** An in-memory token bucket per IP in the four actions (say 30 writes a minute), plus global caps (players at 1000, deletions at 20 an hour) that return a friendly error. Friction: none for humans. Code: forty lines, no dependency; per-instance memory is leaky but enough for a dorm. Options: Upstash Redis for exact limits (extra account), Vercel WAF rate rules (Pro plan), or nothing (accept that one curl loop can void the board).

**Error and loading states.** Add `error.tsx`, `loading.tsx` and `not-found.tsx` in the house style; wrap the remaining database calls in the actions so they return `{ ok: false, error: "Try again" }` and the form keeps its state. Friction: none. Code: an hour. Buys: outages look like a hiccup instead of a broken site.

**Keep the match form when creating an opponent.** Pass `?return=match` and the side, and on success route back with the new player selected (sessionStorage for the draft). Friction: none, it removes some. Code: small. Buys: the first-night flow.

**Idempotency key on recordMatch.** A client-generated UUID per form instance in a nullable unique column, plus `if (pending) return` in `submit()`. Friction: none. Code: one migration, ten lines. Buys: no duplicates from slow taps.

**Load the log once on the player page.** Trivial; halves round trips on the shared page.

### After thirty active players

**Paginate the log** at 100 entries with "older" links, and render the Delete button only on the newest page. **Rank search** prefix matches first and apply the exclusion server-side. **Gate migrations** on `VERCEL_ENV === "production"` so previews cannot alter the live schema. **Cache the replay** in memory keyed on row counts only if p95 page time exceeds about 500 ms; at a few thousand matches it will not. **Optional deletion note** (a free-text "why") only if unexplained deletions actually appear; it costs one field on a rare action.

### Not to do

**Accounts, MIT Touchstone or magic links.** Every version costs the sign-up moment ADR 0001 protects, and attribution is not what stops a dorm cheat; visibility is. **Loser confirms the result.** Already rejected in ADR 0001; the board goes stale. **CAPTCHA or proof-of-work on writes.** Bots are not the threat, residents are, and it punishes the person standing at the table. **Fuzzy-match refusal of similar names.** Two real "Wei Chen"s exist in any large house; keep the nudge, add the normalisation above. **Stored or cached ratings now.** Replay is a few milliseconds and the audit property is the product. **Hiding or physically deleting matches.** Breaks the log; keep `delete-player.sh` for test data only. **Score lines and provisional K.** Both add fields or rules to explain; the ledger already defers them.

## 4. Tests to add

Rating engine (`src/lib/rating.test.ts`):

- A deletion of a match that never existed is ignored.
- A player appearing only in matches, not in `players`, still gets a rating and history.
- Two matches with identical created_at but ids in reverse input order replay by id.
- Doubles and singles between the same four players interleaved: total rating is conserved to 1e-9 at every step, not just the end.
- Deleting the first match of a long log reproduces the replay of the log without it, point for point.
- A restore after a deletion (once added) makes the match count again in its original position.
- Extreme gap: delta is non-negative for the winner and the win count agrees with the winner side.

Actions (with a test database or a mocked `getDb`):

- `createPlayer` rejects empty, whitespace-only and over-60-character names, and collapses internal whitespace.
- `createPlayer` treats NFC and NFD forms, zero-width joiners and a trailing U+200B as the same name once normalisation exists.
- `createPlayer` with two concurrent identical names returns one success and one "already exists" with the existing id.
- `recordMatch` rejects a side of three, unequal sides, repeated ids across sides and a nonexistent id, each with the documented message.
- `recordMatch` with a doubles pair where a2 equals b2 is rejected before the database CHECK.
- `deleteMatch` twice returns "already deleted" the second time and inserts exactly one row.
- `deleteMatch` with a string, a float and a negative number returns "Invalid match id".
- `searchPlayers` with `%`, `_` and `\` returns only literal matches and never every row.
- `searchPlayers` with a query over 60 characters returns an empty list.
- Rate limit (once added): the 31st write from one IP in a minute is refused with a friendly message and the 1st after the window succeeds.
